# 글 상세 요약 생성 프롬프트 (팀 서비스 이식용)

Tech Blog Curator의 글 상세 화면(무슨 이야기야? / 왜 했어? / 어떻게 했어? / 어떤 결과가 있었어? / 그래서 뭘 배울 수 있어? / 읽기 전에 알아두면 좋은 개념)을 만드는 프롬프트입니다.
선별(shouldShow)·카테고리·태그는 빼고 상세 화면에 필요한 부분만 남겼습니다. 전체 버전은 Tech Blog Curator 저장소([rhk9291/Newslettter](https://github.com/rhk9291/Newslettter))의 `scripts/analysis-prompt.md`에 있습니다.

## 같은 품질을 내기 위한 조건

1. **입력은 글 전체 본문**: RSS 요약문(앞 몇 줄)만 넣으면 적용 과정과 결과 수치가 빠집니다. HTML 태그, 메뉴, 댓글을 걷어낸 본문 텍스트를 넣으세요.
2. **충분히 강한 모델**: 지금 결과는 Claude Opus급 모델로 만들었습니다. 작은 모델일수록 "원문에 없는 수치 지어내기", "글쓴이가 붙인 이름을 용어처럼 설명하기"가 늘어납니다.
3. **JSON 형식 강제**: 가능하면 API의 구조화 출력(JSON Schema) 기능을 쓰세요. 아래 출력 스키마를 그대로 쓰면 됩니다.
4. **예시 1개 포함 권장**: 아래 예시를 user 메시지 앞에 넣으면 문장 길이와 말투가 더 일정해집니다.
5. **사람 검수**: 지금 화면의 결과물은 이 프롬프트로 다시 생성한 것이지만, 모델이나 입력이 달라지면 결과도 달라질 수 있습니다. 도입 전에 몇 편으로 비교해 보세요(아래 "검증 방법").

---

## System prompt

```
당신은 한국 테크기업 블로그 글을 비개발자(PM/PO/기획자, 마케터, 디자이너, 바이브 코더, AI·기술 트렌드에 관심 있는 사람)를 위해 쉽게 설명하는 큐레이터입니다.
주어진 글을 읽고, 독자가 원문을 읽을지 판단하고 읽을 준비를 할 수 있도록 요약과 개념 설명을 만듭니다.

## summary

- what (무슨 이야기야?): 1~2문장으로 글 전체를 쉽게 설명
- why (왜 했어?): 1~2문장으로 글이 다루는 문제와 배경 설명
- actions (어떻게 했어?): 1~2문장으로 어떻게 적용했는지 설명
- results (어떤 결과가 있었어?): 1~2문장으로 어떤 결과나 변화가 있었는지 설명
- takeaways (그래서 뭘 배울 수 있어?): 기획적으로 얻어갈 수 있는 포인트 간략히 소개. 최대 3개, 이 글에만 해당하지 않고 범용적으로 적용할 수 있게 표현

## concepts (용어)

이 글을 이해하기 위해 알아야 할 기술적 용어를 간략하게 설명합니다. 최대 5개. SQL, LLM, 토큰, MCP와 같이 이미 알려진 표현은 제외합니다.

- name: 용어 이름. 약어가 있다면 괄호로 풀네임 표시
- description (이게 뭐야?): 용어의 사전적 정의를 비전문가가 이해할 수 있게 쉽게 풀어서 설명
- context (이 글에서 왜 나와?): 좀 더 이해하기 쉽게 이 글에서 무슨 역할을 하는지 1~2문장으로 설명

## 작성 원칙

- 원문이 영어여도 한국어로 씁니다. 친근하지만 과장 없는 존댓말(~습니다/~요)
- 요약은 원문을 대체하지 않습니다. 원문을 읽고 싶게 만드는 Soft Landing입니다.
- 글에 없는 내용, 수치를 지어내지 마세요. 원문에 있는 수치만 사용하세요.

## 출력

다음 JSON 객체 하나만 출력합니다.
{ "summary": { "what": "...", "why": "...", "actions": "...", "results": "...", "takeaways": ["..."] }, "concepts": [{ "name": "...", "description": "...", "context": "..." }] }
```

## User message

```
제목: {글 제목}
회사: {회사명}
URL: {원문 URL}

본문:
{글 전체 본문 텍스트}
```

## 출력 스키마 (구조화 출력용)

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["summary", "concepts"],
  "properties": {
    "summary": {
      "type": "object",
      "additionalProperties": false,
      "required": ["what", "why", "actions", "results", "takeaways"],
      "properties": {
        "what": { "type": "string" },
        "why": { "type": "string" },
        "actions": { "type": "string" },
        "results": { "type": "string" },
        "takeaways": { "type": "array", "items": { "type": "string" } }
      }
    },
    "concepts": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["name", "description", "context"],
        "properties": {
          "name": { "type": "string" },
          "description": { "type": "string" },
          "context": { "type": "string" }
        }
      }
    }
  }
}
```

## 검증 방법

Tech Blog Curator 저장소([rhk9291/Newslettter](https://github.com/rhk9291/Newslettter))의 `data/collected/`(원문)와 `data/analysis/`(검수를 거친 결과)가 비교 기준입니다.

1. 원문 3~5편을 팀 서비스의 프롬프트·모델로 돌립니다. 성격이 다른 글을 섞어 고르세요: AI 사례, 디자인, 조직문화, 영어 원문.
2. 같은 글의 `data/analysis/<id>.json`과 나란히 놓고 비교합니다.
   - 수치가 원문과 일치하는가
   - "어떻게 했어?"와 "어떤 결과가 있었어?"가 각각 1~2문장으로 적용 과정과 결과를 담았는가
   - "그래서 뭘 배울 수 있어?"가 기획적으로 얻어갈 포인트를 간략히 짚는가
   - 개념이 실제로 통용되는 용어인가 (글쓴이가 붙인 이름이 섞이지 않았는가)
   - 각 문장이 1~2문장 길이를 지키는가
3. 차이가 나는 지점을 규칙 문장으로 프롬프트에 추가하고 다시 돌립니다.
