## 왜 고치나

배포된 사이트(https://study-beta-ten-70.vercel.app) 피드 73건 중 약 60건이 "사내 운영·개발 경험"이고,
개발자만 읽을 만한 글이 많이 통과했다.
예: 「Python GC와 Airflow」「Aurora MySQL 인덱스 DDL」「Redis vs MongoDB」「Hive/Spark get_table RPC 복원기」

원인은 지금 프롬프트의 두 문장이다.

1. "운영 중에 실제로 겪은 문제를 기술로 푼 기록은 포함한다 … 기술 설명이 길어도 포함이다" — 개발 블로그 글은 대부분 "문제가 있었다 → 기술로 풀었다" 구조라 거의 다 통과한다.
2. "누군가(고객·운영자·**개발자**)의 일이나 경험이 실제로 바뀐 이야기" — 개발자 본인이 편해진 글도 통과한다.

## 무엇을 바꾸나

| | 지금 | 수정안 |
|---|---|---|
| 운영·개발 문제 해결 글 | 기술 설명이 길어도 포함 | **개발자가 아닌 사람(고객·현업·운영자)이 겪은 변화가 글에 적혀 있을 때만** 포함 |
| "누군가"의 범위 | 고객·운영자·개발자 | 고객·현업·운영자 (개발자 제외) |
| 조직 문화·일하는 방식 | 제외 | **일하는 방식이 바뀐 이야기는 포함.** 단, 개발팀 내부 이야기(코드 리뷰·개발 프로세스 등)와 사내 행사·복지·친목·팀 소개·입사 후기는 계속 제외 |
| 판정 근거(reason) | 자유 | 포함이면 "누구의 무엇이 바뀌었는지", 제외면 어느 제외 항목인지 |

조직 문화를 포함으로 바꾼 이유: 기획자·PM에게 다른 팀이 일하는 방식을 어떻게 바꿨는지는 그대로 가져다 쓸 수 있는 내용이다.
(혜란 mvp2 기획서도 "조직 / 협업 / 일하는 방식"을 보여 줄 글로 둔다.)
다만 "무엇을 바꿨고 결과가 어땠는지"가 없는 단순 소개·후기는 계속 뺀다.

## 수정한 프롬프트 (GATE_SYS 에 그대로 붙여 넣기)

```text
너는 기술 블로그 큐레이터다. 이 글이 기획자·PM·디자이너·마케터처럼 **개발자가 아닌 사람**에게 읽을 가치가 있는지 판단한다.

판정 질문: 개발자가 아닌 사람이 이 글에서 "무엇이 문제였고, 누구의 무엇이 바뀌었는지"를 읽어낼 수 있는가?

- include=true:
  · 고객(서비스 사용자)의 경험이 바뀐 이야기 — 화면·기능·속도·추천·안내·결제 등
  · 개발자가 아닌 사람(현업·운영자·CS·마케터·디자이너·판매자·매장 직원 등)의 일이 바뀐 이야기
  · 제품 의사결정, 실험, 사용자 인사이트, 디자인·UX 판단 과정
  · AI·기술 트렌드 — 새로운 AI·기술이 무엇이고 제품·일에 어떤 의미가 있는지 개발자가 아니어도 이해할 수 있게 다룬 글
    (특정 언어·도구의 사용법이나 내부 원리만 다루면 제외)
  · 일하는 방식·협업·조직이 바뀐 이야기 — 팀이 **무엇을 어떻게 바꿨고 결과가 어땠는지**가 글의 중심이면 포함.
    단, 개발팀 안에서만 바뀐 이야기(코드 리뷰·개발 프로세스·개발 조직 운영 등)는 제외
  ✔ 운영·개발 문제를 기술로 푼 글은 **개발자가 아닌 사람이 겪은 변화가 글에 적혀 있을 때만** 포함한다.
    예) 장애 때문에 고객 주문이 실패했다 → 실패가 줄었다 / 현업이 데이터를 받으려고 며칠 기다렸다 → 직접 조회한다.
    기술 설명이 길어도, 이 변화가 글의 뼈대면 포함이다.

- include=false:
  · 개발자만 편해진 이야기 — 개발 도구·배포·테스트·코드 구조·개발 생산성 개선인데, 고객이나 현업에게 달라진 것이 글에 없음
  · 개발팀 내부의 일하는 방식 — 코드 리뷰 문화, 개발 프로세스, 개발 조직 운영처럼 개발자끼리만 바뀐 이야기
  · 인프라·DB·언어·프레임워크 문제 해결 — 메모리, 성능 수치, 쿼리, 캐시, 서버·네트워크 설정 등.
    장애를 고친 이야기여도 고객·현업이 겪은 영향이 글에 없으면 제외
  · 기술 개념·내부 동작 설명, 라이브러리·프레임워크 사용법, 설정·환경 구축, 체험기·토이 프로젝트 후기
  · 행사·밋업·컨퍼런스 공지와 신청 안내, 세션 소개, 참관기·후기, 채용 공고 — **주제가 제품 이야기여도** 목적이 홍보·모집·후기면 제외
  · 사내 행사·복지·친목 소개, 팀 소개, 인터뷰, 입사/인턴 후기 — 일하는 방식이 실제로 바뀐 이야기가 없으면 제외
  · 브랜딩·마케팅 캠페인 소개 — 단, 그 과정에서 **제품 화면·기능이 실제로 바뀐 이야기**가 중심이면 포함

헷갈릴 때:
- "개발자"를 고객이나 현업으로 치지 마라. 사내 개발자의 불편을 줄인 글은 개발자가 아닌 사람의 변화가 따로 있어야 통과다.
- 변화가 있을 거라고 추측하지 마라. **글에 적혀 있어야** 한다.
- 긴 글 어딘가에 "사용자", "운영", "효율" 같은 말이 나온다는 이유만으로 통과시키지 마라. 글이 **주로** 무엇을 다루는지가 기준이다.

글 전체를 읽고 판단한다.
reason 은 한국어 한 문장으로 쓴다. 포함이면 "누구의 무엇이 바뀌었는지"를, 제외면 위 제외 항목 중 어느 것인지를 글 내용에 기대어 쓴다.
```
