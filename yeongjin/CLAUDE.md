# 테크 블로그 아카이빙 서비스 — 프로젝트 규칙 (CLAUDE.md)

이 파일은 이 폴더에서 작업하는 모든 세션이 따르는 **고정 규칙**입니다.
현재는 **PRD만 존재하고 코드는 아직 없는 기획 단계**입니다. 구현을 시작하기 전에 반드시 정본 문서를 먼저 확인하세요.

## 언어
- 사용자와의 모든 소통·설명·주석은 **한국어**. 코드 식별자(변수·함수·타입)는 관례상 영문 사용.

## 무엇을 만드는가
- 소규모 팀(10~30명) 전용 **기술 블로그 아카이빙 + 토론 서비스**. 팀원들이 네이버/컬리/당근마켓/토스/우아한형제들/오늘의집 등 기술 블로그 글을 모으고, AI 요약/형광펜으로 쉽게 읽고, 댓글·토론으로 함께 논의한다.
- **정본 문서(반드시 이걸 기준으로)**: [`테크블로그_아카이빙_서비스_PRD_1.md`](./테크블로그_아카이빙_서비스_PRD_1.md)
  - 2장: 하단 탭바 IA (탐색/큐레이션/검색/마이)
  - 3장: 핵심 기능 명세 (3.1~3.11)
  - 4장: 대표 사용자 플로우
  - 5장: 화면 구성 및 카드 공통 규격(5.0)
  - 6장: 기술 스택 및 AI 연동 방안
  - 8장: MVP 범위
  - 9장: **확정된 정책(9.1) / 남은 오픈 이슈(9.2)** — 기능을 임의로 설계하기 전에 반드시 확인

## 확정된 핵심 정책 (PRD 9.1 요약 — 상세는 PRD 원문 참조)
- 원문 본문 전체를 자체 저장해 서비스 내에서 렌더링(하이라이트 기능 지원 목적), 팀 내부 전용 비공개
- 형광펜은 **팀 공개가 기본값**(토글로 개인 전용 전환), 개인 메모는 **비공개가 기본값**(토글로 팀 공개 전환) — 서로 반대 방향 기본값이므로 혼동 주의
- 글 삭제는 소프트 삭제 후 유예기간을 두고 영구 삭제
- 등록 시 카테고리·원문 URL만 필수, 등록 노트(핵심 인사이트/정리할 지식/적용할 점)는 권장이며 건너뛰기 가능. 자동 수집 글·건너뛴 글 모두 팀원 누구나 나중에 노트 추가 가능
- 자동 수집은 실시간에 가까운 주기(5~15분)로 RSS 폴링
- 큐레이션 탭은 온보딩 강제 없이, 탭 내 질문형 키워드 칩 선택 → 카테고리 매칭, 부족 시 이번 주 인기(조회수) 글로 보충
- "다 읽음"은 스크롤 비율 90% 도달 시 자동 판정(체류 시간 등 보조 지표 없음)
- 인라인 댓글/메모의 `내 의견` / `용어·개념 정리 필요` 유형 선택은 **선택 사항**(강제 아님)
- 토론: 참여 인원 제한 없음, 중도 이탈 허용, 개설자만 종료 가능, MVP는 팀 전체 브로드캐스트 알림
- 웹 우선 출시(Next.js), 앱은 이후 확장

## 아키텍처 방향 (예정, PRD 6장 근거 — 실제 구현 시 이 방향을 기본값으로 따름)
- **Frontend**: Next.js (웹 우선)
- **Backend**: Node.js(NestJS) 또는 Python(FastAPI)
- **DB**: PostgreSQL
- **AI 연동**: Gemini Flash/Flash-Lite(글 전체 요약, 비동기 파이프라인) + Groq(형광펜 구간 실시간 설명), 폴백 체인 및 한도 초과 대응은 PRD 6.2.2~6.2.3 참조
- **자동 수집**: 회사별 RSS/Atom 피드 폴링 스케줄러, 회사별 수집 어댑터 구조 권장

## 개발 착수 시 워크플로우
1. **먼저 PRD를 정독**하고, 만들려는 화면/기능이 몇 장 몇 절에 해당하는지 확인한다.
2. PRD에 없는 기능·정책을 임의로 추가하거나 다르게 해석하지 않는다. 애매한 부분은 PRD 9.2(남은 오픈 이슈)에 있는지 먼저 확인하고, 없다면 사용자에게 질문한다.
3. 화면 설계/DB 스키마 설계 문서를 새로 만들면 이 파일에 정본 문서 목록으로 추가하고, 이후 세션은 그 문서를 함께 참조하도록 갱신한다(예: miran 팀원 폴더의 `claude_code_handoff/` 구조 참고 가능).
4. PRD의 정책이 사용자와의 논의로 바뀌면, 코드보다 **PRD를 먼저 갱신**하고 그 다음 구현을 맞춘다 — PRD가 항상 최신 정본이어야 한다.

## 하지 말 것
- PRD를 확인하지 않고 화면 구조나 정책을 상상해서 만들기
- PRD 9.1에서 이미 확정된 정책(예: 형광펜 기본 공개 여부, 삭제 방식, 등록 노트 필수 여부)을 임의로 다르게 구현하기
- 확정되지 않은 오픈 이슈(9.2)의 값을 임의로 정해서 코드에 하드코딩하기 — 사용자에게 먼저 확인
- PRD 변경 없이 코드에서만 정책을 바꾸고 넘어가기
