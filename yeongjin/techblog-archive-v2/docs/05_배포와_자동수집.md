# 배포와 자동 수집

> 글 데이터는 **Supabase**(Postgres)에 있고, 새 글은 **Supabase 예약 작업**이 배포된 서비스를 깨워 자동으로 모은다.
> 2026-10-08 로컬 SQLite(`data/app.db`)에서 옮겼다. `data/app.db` 와 `data/backup/` 은 옮기기 전 기록으로만 남긴다.

## 1. 구조

```
[Supabase pg_cron]  매일 07:00 ─▶ POST /api/cron/collect   새 글 모으기(대기로 저장) · 썸네일
                    15분마다   ─▶ POST /api/cron/process   대기 글을 3건 안팎씩 판정 → 분석 → 가이드 → 분류
                                     │  Authorization: Bearer CRON_SECRET 이 맞아야만 돈다
                                     ▼
[배포된 서비스(Next.js)] ── service_role 키 ──▶ [Supabase articles 테이블]  ◀── 화면이 읽는다
                         ── GEMINI_API_KEY ──▶ [Gemini]
```

- **원문 보호** — `articles` 는 RLS 를 켜고 정책을 두지 않았다. 브라우저용 anon 키로는 한 줄도 읽을 수 없고, 서버의 `service_role` 키만 읽고 쓴다. 원문은 GitHub 에도, 화면에도 나가지 않는다(화면은 짧은 발췌 + 원문 링크 — 00 "원문을 얼마나 보여 주나").
- **접근 제한(선택)** — 서비스는 외부 공개가 기본이다. QA 기간처럼 팀만 보게 하려면 배포 환경변수에 `SITE_PASSWORD`(와 `SITE_USER`, 기본 `insight`)를 넣으면 접속 때 로그인 창이 뜬다(`src/proxy.ts`). 자동 수집 주소는 영향을 받지 않는다.
- **나눠 돌기** — 배포 서버는 한 번 실행에 쓸 수 있는 시간이 정해져 있다(최대 300초로 설정). 그래서 모으기와 처리를 나누고, 처리는 200초 예산 안에서 최신 글부터 몇 건씩 한다. 남은 글은 다음 15분 실행이 잇는다.
- **겹침 방지** — 이전 실행이 아직 돌고 있으면 새 실행은 바로 끝난다(`try_lock`).
- **실패 반복 방지** — 글마다 자동 처리 시도 횟수(`attempts`)를 센다. 3번 실패한 글은 건너뛴다 → `npm run collect` 나 `npm run regenerate` 로 사람이 처리.
- **Gemini 하루 한도** — 걸리면 그 실행은 멈추고, 한도가 풀린 뒤(한국 오후 4~5시) 다음 실행이 잇는다. 새 글 1건에 호출 5회 안팎이라 평소에는 한도에 닿지 않는다.

## 2. 처음 설정하는 순서

| 순서 | 어디서 | 할 일 |
|---|---|---|
| 1 | Supabase SQL Editor | [`supabase/schema.sql`](../supabase/schema.sql) 실행 — 테이블·잠금 함수 (완료 2026-10-08) |
| 2 | 터미널 | `npm run migrate-to-supabase` — 로컬 SQLite 글을 id 그대로 옮김 (완료 2026-10-08, 90건) |
| 3 | 배포(Vercel) | 아래 환경변수를 넣고 배포. `vercel.json` — 서울 리전(icn1), 빌드 때 회사 로고를 받는다(실패해도 배포는 계속, 이름 첫 글자로 표시). `.vercelignore` — 로컬 DB·백업·비밀값은 올리지 않는다 |
| 4 | Supabase SQL Editor | [`supabase/cron.sql`](../supabase/cron.sql) 의 `<배포 주소>` `<CRON_SECRET>` 을 바꿔 실행 — 예약 등록 |
| 5 | Supabase SQL Editor | `select * from cron.job_run_details order by start_time desc limit 10;` 로 실행 기록 확인 |

### 배포 서버 환경변수

| 이름 | 값 | 비고 |
|---|---|---|
| `SUPABASE_URL` | 프로젝트 URL | |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role 키 | **비밀** — 서버에만. 화면 코드(클라이언트)에서 쓰지 않는다 |
| `GEMINI_API_KEY` | Gemini 키 | **비밀** |
| `CRON_SECRET` | 임의의 긴 문자열 | **비밀** — `cron.sql` 에 넣는 값과 같아야 한다 |
| `SITE_PASSWORD` · `SITE_USER` | (선택) | 넣으면 사이트 전체에 로그인 창 — 팀만 볼 때 |

로컬에서는 같은 값을 `.env.local` 에 둔다(GitHub 에 올라가지 않는다).

## 3. 사람이 직접 돌리는 명령 (로컬)

| 명령 | 하는 일 |
|---|---|
| `npm run collect` | 지금 바로 새 글 모으기 + 대기 글 전부 처리 (자동 실행과 같은 결과, 시간 제한 없음) |
| `npm run collect -- 5 --only=gangnamunni` | 한 회사만 |
| `npm run regenerate` | 기준이 바뀐 뒤 이미 모은 글 전체를 다시 |
| `npm run report` | 회사별 수집·포함·제외·대기 건수 |

로컬 명령도 Supabase 를 읽고 쓴다 — 로컬에서 돌린 결과가 배포된 화면에 바로 보인다.

## 5. 점검

- 자동 수집이 도는지: `select jobname, status, start_time from cron.job_run_details order by start_time desc limit 10;`
- 서버가 뭐라고 답했는지: `select status_code, content::text from net._http_response order by created desc limit 5;` — `{"ok":true,"processed":…,"left":…}`
- 대기 글이 쌓여만 가면: `select id, title, attempts from articles where status='pending' order by published_at desc;` — attempts 3 인 글은 자동 처리에서 빠졌다는 뜻.
