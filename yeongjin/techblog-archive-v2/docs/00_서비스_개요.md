# 00 · 서비스 개요

> 처음 보는 팀원이 가장 먼저 읽는 문서. 무엇을, 왜, 어떻게 만드는지 한 번에 훑는다.
> 자세한 규칙은 [01_분류기준](./01_분류기준.md) → [02_홈배치기준](./02_홈배치기준.md) 순서로 이어진다.

## 1. 한 줄로

**국내 테크 블로그 글을 "누구의 어떤 부담을 덜어준 글인가"로 다시 묶어, 기획자가 자기 서비스에 옮겨 쓸 사례를 찾게 한다.**

## 2. 왜 만드나

| 지금의 테크 블로그 | 그래서 기획자는 | 이 서비스는 |
|---|---|---|
| 기술 이름으로 쓰여 있다 ("Lynx", "RAG", "낙관적 락") | 제목만 보고는 내 문제와 관련 있는지 모른다 | **사용자가 덜게 된 부담**(기다림, 헤맴, 반복 입력 …)으로 묶는다 |
| 원문이 길고 개발 용어가 많다 | 끝까지 읽기 어렵다 | **쉬운 말 카드 문장**과 **질문형 칸**("더 들어가 볼까요?")으로 풀어 준다 |
| 회사마다 흩어져 있다 | 비슷한 문제를 다른 회사가 어떻게 풀었는지 비교하기 어렵다 | 같은 경험 아래 **여러 회사 사례**를 모은다 |

## 3. 사용자가 보는 화면

| 화면 | 주소 | 하는 일 |
|---|---|---|
| 홈 | `/` | 새로 들어온 글 · 경험별 사례 · 회사별 문제 카드 · 요즘 자주 나오는 기술 |
| 경험 페이지 | `/experiences/…` | 한 경험(예: 기다리지 않아도 되는 경험)의 사례를 **방식별로** 묶어 보기 |
| 기술 페이지 | `/tech/…` | 한 기술 키워드로 쓴 글 모아 보기 |
| 글 상세 | `/articles/…` | 회사 → 원제목 → 핵심 카피 → 핵심 내용 → 결론(BEFORE → AFTER), 기획자 관점 바텀시트, "더 들어가 볼까요?", 원문에서 짚어 볼 문장, **원문에서 보기 ↗**(원래 블로그로 이동) |
| 피드 | `/feed` | 전체 글 최신순 + 회사·태그 필터 + **읽은 글 / 안 읽은 글** 필터 |
| 검색 | `/search` | 자유 검색 + 질문형 추천 |
| 마이 | `/my` | 저장한 글·읽은 글 (로그인 없음 — 이 브라우저에만 저장) |
| 제외된 글 | `/excluded` | AI 가 뺀 글과 그 이유 공개 |

> **메뉴** — 홈·피드·검색·마이는 PC·모바일 모두 **화면 아래 탭바**로 오간다. 맨 위 바에는 로고와(홈에서만) "내가 읽은 글" 스위치만 있다.
>
> **읽은 글 구분** — 글 상세를 열면 "읽음"이 된다(상세 상단에서 "안 읽음"으로 되돌릴 수 있다). 글 카드에 ✓ 읽음 표시가 붙어 흐려지고, 피드·검색 결과·경험 페이지·기술 페이지 목록 위의 "전체 / 안 읽은 글 / 읽은 글"로 거를 수 있다. 고른 값은 다음에 와도 유지된다. 기록은 이 브라우저에만 남는다. 홈에서는 맨 위 바 오른쪽의 **"내가 읽은 글" ON/OFF** 로 고른다 — OFF 면 새 글 카드·기술 탭 목록·문제 카드에서 읽은 글을 빼고 안 읽은 글로 채운다.

## 4. 데이터가 흐르는 길

글 하나가 들어와서 홈에 놓이기까지. **단계 번호는 기준 문서의 단계 번호와 같다.**

| 흐름 | 단계 | 무엇을 하나 | 코드 | 기준 문서 |
|---|---|---|---|---|
| ① 모으기 | 0 | 18개 블로그에서 글·썸네일·로고를 가져온다 | `core/0-collect` | 01 · 0단계 |
| ② 읽기 | 1 | 기획 관점이 없는 글을 뺀다 (이유 공개). **본문 전체**를 읽는다 | `core/1-analyze` | 01 · 1단계 |
| | 2 | 글을 질문형 칸 3~6개로 나눈다 ("더 들어가 볼까요?"). 글 끝까지 모든 문단을 보고 뼈대를 잡은 뒤, 칸마다 근거 문단 **전문**을 다시 읽는다 | `core/1-analyze` | 01 · 2단계 |
| ③ 경험으로 묶기 | 3~6 | 칸마다 **누가 → 어떤 어려움 → 어떤 부담 → 어떻게 덜었나**를 읽고, 글의 경험과 적합도를 정한다 | `core/2-classify` | 01 · 3~6단계 |
| | 7~8 | 방식·기술을 붙이고, 누구나 읽는 카드 문구를 쓴다 | `core/2-classify` | 01 · 7~8단계 |
| ④ 홈에 놓기 | 9~13 | 경험·적합도·기술을 읽어 홈의 자리마다 고르고 줄 세운다 | `core/3-place` | 02 |
| ⑤ 화면 | — | 결과를 보여준다 | `app` · `components` | — |

①~③은 **매일 자동으로** 돈다 — Supabase 예약 작업이 배포된 서비스를 깨워 새 글을 모으고 분석해 Supabase DB 에 저장한다(로컬에서 `npm run collect` 로 바로 돌릴 수도 있다). ④는 화면을 열 때마다 저장된 결과로 계산한다. 설정: [05_배포와_자동수집.md](./05_배포와_자동수집.md)

> **원문을 얼마나 보여 주나** (2026-10-08 결정) — 외부 공개 서비스라 **원문 전체는 싣지 않는다.** 각 회사 블로그 글은 저작물이라 전문을 다시 보여 주면 복제·전송에 해당할 수 있기 때문이다. 화면에는 AI 가 새로 쓴 정리와 **짧은 발췌**(핵심 문장 20~120자, 칸별 근거 문장 120자 안)만 출처와 함께 보여 주고, 전체 글은 "원문에서 보기 ↗"로 원래 블로그에서 읽게 한다. 원문은 분석용으로 서버 DB 에만 둔다(화면·브라우저로 보내지 않는다).
>
> **원문을 얼마나 읽나** (2026-10-07부터) — 배제 판정·상세 분석(핵심 카피·결론·BEFORE/AFTER)은 **본문 전체**를 읽는다. "더 들어가 볼까요?"는 먼저 **글 끝까지 모든 문단**을 문단당 앞 300자씩 보고 칸을 세운 뒤(전체 글자의 약 95% — 300자를 넘는 문단은 4%), 칸마다 근거로 고른 문단은 **전문**을 다시 읽고 쓴다. 경험 분류는 이 칸을 근거로 한다. 예전에는 앞 3,000자 · 14,000자 · 문단당 140자(전체 5,000자) 제한이 있었다.

## 5. 핵심 개념 다섯 가지

| 개념 | 한 줄 | 자세히 |
|---|---|---|
| **부담 → 경험** | 해결 **전에** 사람이 겪던 부담 7가지(기다림·헤맴·비교·입력·재설명·수작업·확인)가 각각 하나의 경험이 된다 | 01 · 4단계 |
| **경험 사슬** | 누가 → 어떤 어려움 → 어떤 부담 → 어떤 기술로 어떻게 덜었나. 고리가 끊기면 경험이 없다 | 01 · 3단계 |
| **적합도** | STRONG(분명히 덜어냄) / WEAK(덜었다고 볼 수도 있음) / NONE(해당 없음). 홈 경험 자리는 STRONG 만 센다 | 01 · 6단계 |
| **누구의 부담** | 서비스 사용자 / 사내 운영자 / 개발자. 사내 경험도 같은 경험으로 세고 "사내 운영·개발 경험" 태그로만 구분 | 01 · 5단계 |
| **AI 는 쓰고, 코드가 정한다** | AI 는 칸을 읽고 문장을 쓴다. 경험·적합도·탈락은 코드 규칙이 정한다 | 01 · 6단계 |
