## 1. 메인 화면 "제외된 글" 영역 삭제 + 제외 정책 재검토

### 1-1. 문제

1. 메인 화면(`src/app/page.tsx`)에 "제외된 글 {수}" 링크가 노출되어, 큐레이션되지 않은 글의 존재가 메인에서 바로 보였다.
2. 1차 게이트(`gateArticle`, `src/core/1-analyze/analyze.ts`)가 "순수 기술 구현 디테일"이라는 이유로 제외한 글이 너무 많이 쌓여 있었다(전체 제외 60건). 그런데 그 60건을 실제로 열어보면 **행사·컨퍼런스·채용공고 같은 홍보성 글**과 **기술적으로 어렵지만 기획자가 봐도 되는 글**이 뒤섞여 있었다 — 게이트 기준이 지나치게 보수적으로 작동한 결과였다.

### 1-2. 해결

**(a) 메인 화면 링크 제거**

`src/app/page.tsx`에서 "제외된 글 {counts.excluded}" 링크를 삭제했다. 포함 글 수를 보여주는 문장은 그대로 남겼다.

```diff
- <p className="mt-6 flex flex-wrap items-center gap-x-3 gap-y-1 text-sm text-ink-3">
-   <span>국내 테크 블로그 글 {counts.included}건을 사용자가 덜게 된 부담으로 다시 묶었어요.</span>
-   <Link href="/excluded">제외된 글 {counts.excluded}</Link>
- </p>
+ <p className="mt-6 text-sm text-ink-3">
+   국내 테크 블로그 글 {counts.included}건을 사용자가 덜게 된 부담으로 다시 묶었어요.
+ </p>
```

`/excluded` 페이지 자체는 남겨 두었다(투명성 공개 목적) — 메인에서 들어가는 입구만 없앴다.

**(b) 제외 정책 재검토 — "행사 글만 제외로 남기고 나머지는 전부 포함"**

제외 사유(`exclusion_reason`)는 1차 게이트가 자유 문장으로 쓴 한국어 한 문장이다. 이 문장에 행사 관련 어휘가 있는지로 "행사 글"을 가려내는 스크립트를 새로 만들었다: [`scripts/run/reinclude-non-event.mts`](../scripts/run/reinclude-non-event.mts)

- 판정 어휘: `행사, 컨퍼런스, 콘퍼런스, 밋업, 미트업, 세미나, 서밋, Summit, 참관기, 세션 소개, 신청 안내, 채용 공고, 모집`
- 애매해서 위 어휘가 하나도 없으면 "포함"쪽으로 둔다 — 사용자가 "나머지는 모두 포함"이라고 명시했기 때문.
- 먼저 `--apply` 없이 미리보기만 돌려 분류 결과를 사용자에게 확인받은 뒤, `npm run reinclude-non-event -- --apply`로 실제 반영했다.
- 포함으로 되돌리는 글은 단순히 `status`만 바꾸지 않고, `rebuildIncluded(id, { reanalyze: true, reguide: true })`로 분석·"더 들어가 볼까요?" 가이드·경험 분류를 전부 새로 만들어 저장했다(게이트를 다시 통과시키는 게 아니라 게이트를 건너뛰고 바로 분석 단계로 보낸다).

### 1-3. 결과

전체 제외 글 60건을 검토해 **35건은 행사/컨퍼런스/밋업/채용공고 성격으로 제외 유지**, **25건은 포함으로 되돌렸다**(기술적으로 너무 어려운 글, 개념 설명, 조직문화, 브랜딩, 뉴스레터 모음, 토이 프로젝트 후기 등).

- 스크립트 추가 커밋: `e7ac02f`에 `scripts/run/reinclude-non-event.mts`와 `package.json`의 `reinclude-non-event` 스크립트 항목이 함께 포함되었다(검색 수정과 같은 커밋에 묶임).

## 2. 검색 결과가 제목과 무관한 글을 보여주는 버그 수정

### 2-1. 문제

`src/core/shared/db.ts`의 `searchArticles`가 분석 결과(`learning`)와 "더 들어가 볼까요?" 가이드(`guide`) 전체를 `JSON.stringify`로 문자열화한 뒤 통째로 부분 문자열 검색을 했다.

```ts
// 수정 전
export async function searchArticles(q: string): Promise<ArticleRow[]> {
  const needle = q.toLowerCase();
  return (await listArticles("included")).filter((a) =>
    [a.title, a.companyId, JSON.stringify(a.learning ?? ""), JSON.stringify(a.guide ?? "")]
      .some((s) => s.toLowerCase().includes(needle)),
  );
}
```

이 방식은 두 가지 구체적인 버그를 만들었다:

1. **스키마 키 이름까지 검색됨** — `JSON.stringify`는 `"problem"`, `"terms"`, `"outcome"` 같은 필드 이름도 그대로 문자열에 남긴다. 그 필드가 채워진 글은 검색어와 무관하게 걸릴 수 있었다.
2. **영문 단어 내부의 부분 문자열까지 매칭됨** — 예를 들어 "AI"로 검색하면 "dom**ai**n", "det**ai**l", "cont**ai**ner" 같은 전혀 무관한 영단어 안에서도 매칭됐다.

실측: "AI" 검색 시 169건이 나왔는데, 그중 131건은 제목에 "AI"가 없었다. 예: "컨테이너처럼 쓰고, VM처럼 격리하기"(container → "ai" 포함) 같은 글이 섞여 나왔다.

### 2-2. 해결

`src/core/shared/db.ts`를 다음과 같이 바꿨다:

1. `JSON.stringify` 대신, 사람이 실제로 쓴 문장·단어만 모아 검색용 텍스트를 만드는 `learningText()` / `guideText()`를 추가했다. 원문 그대로 발췌한 근거 문장(`originalExcerpt`)은 제외해 노이즈를 더 줄였다.
   - `learningText`: `cardHeadline`, `hook`, `tags`, `conclusion`, `before`/`after`, `productPatterns`, `plannerQuestions`, `quickView`(summary/whyItMatters/keywords), `problem.items`, `technology`, `experienceImpact`, `discussionQuestions`, `problemCard`, `overview`, `concepts`, `tools`
   - `guideText`: `lead`(what/why/how/soWhat), `points`, `sections`(question/problem/paras/outcome/terms), `terms`
2. 영문·숫자로만 이루어진 검색어는 단어 경계(`\b`)로 매칭해 "AI"가 "domain"/"detail" 안에서 걸리지 않게 했다. 한글 검색어는 기존처럼 부분 문자열 매칭을 유지한다(한글은 "결제"가 "결제하기" 안에서 걸리는 게 정상 동작이라 다르게 다뤘다).

```ts
const ASCII_WORD = /^[a-z0-9+#.]+$/i;
function textMatches(haystack: string, needle: string): boolean {
  if (ASCII_WORD.test(needle)) {
    const esc = needle.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
    return new RegExp(`\\b${esc}\\b`, "i").test(haystack);
  }
  return haystack.toLowerCase().includes(needle.toLowerCase());
}
```

### 2-3. 결과

"AI" 검색 결과가 **169건 → 105건**으로 줄었다. 줄어든 64건은 전부 스키마 키 누수 또는 영단어 내부 매칭으로 생긴 가짜 결과였다(검증: 실제 Supabase 데이터로 재실행해 확인). 남은 105건 중 제목에 "AI"가 없는 67건은 샘플 확인 결과 전부 **본문에서 실제로 AI를 다루는 진짜 관련 글**이었다(예: 제목엔 없지만 본문에서 "AI 에이전트(MCP) 연동"을 다루는 글).
