## 0. 한 줄

**테크 블로그를 비개발자(기획자·디자이너·마케터)가 끝까지 읽게 만드는 앱.**

읽을 거리를 모아주는 앱은 많다. 이 앱이 다른 점은 **읽다가 막히는 지점을 없애는 것**이다.
그래서 기능의 절반이 "읽기"에, 나머지가 "읽은 것을 남기기"에 쓰인다.

### 누구를 위한 것인가

개발 지식이 없는 사람이 기준이다. 개발자도 쓸 수 있지만, **어느 쪽을 택할지 애매하면
비개발자 쪽을 택한다.** 개발자는 원문을 그냥 읽으면 되기 때문이다.

### 세 가지 약속

1. **원문을 바꾸지 않는다.** 우리가 얹는 건 안내뿐이다. 요약이 원문을 대체하지 않는다.
2. **AI가 틀려도 화면이 깨지지 않는다.** 만들어진 게 없으면 그 칸만 숨기고 나머지는 그대로 뜬다.
3. **숫자로 벌주지 않는다.** 연속 0일, 활동 0건 같은 건 보여주지 않는다.
   0 이면 **칸째 숨긴다** — 조회수·인사이트 수·공감·완독률·이번 달 수치 전부 같은 규칙이다.
   갓 수집된 글에 "👁 0 💬 0" 이 붙으면 아무도 안 본 글처럼 보이고, 저장만 하고 아직
   안 읽은 사람에게 "0%" 게이지를 보여주면 시작도 전에 벌점을 주는 셈이다.

## 2. 기능 목록

### 2.1 읽기 — 이 앱의 본체

| 기능 | 어디에 | 무엇을 하나 |
|---|---|---|
| **요약 한 줄** | 히어로 | 대표 이미지 위에 제목 + 이 글이 무슨 얘긴지 2문장 |
| **알아두면 편해요** | 글 상세 | 이 글에서 뜻을 모를 말 최대 **8개**. 영어 약어·업계 은어 + **한국어인데 뜻이 다른 말**(적재·정산·롤백)까지 |
| **한눈에** | 글 상세 | **무슨 일이에요? / 왜 했대요? / 그래서 뭐가 달라졌어요?** 세 질문에 각 2~3문장. 이게 본문 역할을 한다 |
| **기획 포인트** | 글 상세 | 기획자가 이 글을 어떤 눈으로 볼 것인가, 1~2문장. **원문에 판단·트레이드오프가 없으면 비운다** |
| **더 들어가 볼까요?** | 글 상세 | **질문형 소제목** 2~3개 + 답 문단. 없으면 통째로 숨김 |
| **원문에서 확인** | 더 들어가 볼까요 | 칸마다 눌러서 근거가 된 원문 문단을 그 자리에서 편다 |
| **용어 밑줄** | 한눈에·더 들어가 | 어려운 단어에 자동 밑줄 → 누르면 하단에서 뜻 |
| **원문 읽기** | 글 상세 · 플로팅 "원문" | **앱 안에서 읽는다.** 누르면 밑줄 섹션으로 스크롤되며 펼쳐진다(§2.2 원문 밑줄). 밑줄이 여기서만 되기 때문이다 |
| **원본 페이지** | 밑줄 섹션 안 작은 링크 · 본문 못 뽑은 글은 카드 | 앱 안 웹뷰. 이미지·표가 많은 글은 원본이 낫다. 본문 추출 실패 시엔 이 문만 남는다 |
| **글자 크기** | 글 상세 | 가/가 두 단계 |
| **다음 글** | 플로팅 | 추천에서 다음 글로 바로 이동 |
| **난이도 배지** | 목록·상세 | 술술 / 용어 있음 / 코드 있음 |

> **읽기시간은 표시하지 않는다.** 사람마다 다르고, 숫자가 붙으면 "오래 걸리는 글"로 읽혀
> 아예 안 들어온다. 난이도 배지가 그 역할을 한다.

### 2.2 남기기 — 읽고 끝나지 않게

| 기능 | 어디에 | 무엇을 하나 |
|---|---|---|
| **생각해볼 질문** | 글 상세 | 글이 내린 판단을 파고드는 질문 1개. 빈 종이보다 답하기 쉽다 |
| **원문 밑줄** | 글 상세 — 요약 아래 **접이식**("원문 읽으며 밑줄 긋기") | 문장을 누르면 밑줄(5색)+메모. **나만 보기.** 기본은 접혀 있다(펼쳐 두면 아래 질문·인사이트까지 못 내려간다). 플로팅 "원문"이 이 칸을 연다. 웹뷰에서는 남의 페이지라 안 된다 |

> **"원문을 보러 가볼까요?" 카드는 지웠다.** 앱에서 읽을 수 있는데 나가는 문을 크게 열어 두면,
> 밑줄도 기록도 남지 않는다. 본문을 못 뽑은 글에서만 그 카드가 뜬다.
| **스탬프** | 글 상세 | 다 읽으면 뜨는 탭 한 번짜리 반응 4종 — **도움이 됐어요 / 용어가 어려웠어요 / 반대 의견이 있어요 / 인상적이었어요**. 제목("다 읽으셨네요, 어떠셨어요?")은 스탬프 카드 안에만 둔다 |
| **인사이트 쓰기** | 글 상세 → 쓰기 | **질문 3개에 답하는 형식.** ① 우리라면 같은 선택을 할 수 있을까요(판단 → core) ② 우리 제품 어디에 먼저 적용해볼까요(착지점 → apply) ③ 왜 그 방법이면 풀린다고 봤을까요(가설의 근거 → hypothesis) + 자유롭게 남기는 칸. 하나만 답해도 저장된다. 밑줄이 있으면 ①에 AI가 초안을 채워준다 |

> **질문을 왜 이렇게 바꿨나.** 예전 ①은 "이 글에서 무엇을 보셨나요"였다. 그런데 상세가 이미
> 무슨 일·왜 했나·뭐가 달라졌나를 말해 주므로(ReadingDigest), 그 답은 **요약을 옮겨 적은 것**이
> 된다. 그래서 요약에 없는 것만 묻는다 — ① 우리 조건에 대입했을 때의 **판단**, ② 고유명사로
> 떨어지는 **착지점**(화면·기능 이름), ③ 글 쓴 쪽이 세운 **가설의 근거**.
> ③은 **원인을 묻지 않는다** — 원인("결제 실패가 반복됐다")은 상세가 이미 말해 주므로 되물으면
> 답이 본문 베끼기가 된다. 글에 없는 건 원인과 해법 **사이의 연결**, 즉 "그 방법이면 이게
> 해소된다"고 본 근거다. 그 연결을 추론하는 연습이 자기 가설을 세우는 힘이 된다.
> ③이 맨 뒤인 이유: 셋 중 가장 품이 든다. 중간에 그만두어도 앞 둘은 남아야 한다.
> 질문 문장은 글마다 다르다 — 저장된 LLM 질문(게이트 통과분) → 결정 카드로 조립 →
> **상세 "1분 이해"의 '뭘 했대요?' 인용** → 한 줄 요약 → 유형 템플릿 순으로 내려가되
> **끝까지 답할 수 있는** 질문을 준다. 유형 문구만 남는 단계에서도 "~ 방법 하나는 무엇이고"
> 처럼 **무엇을 말하는지 먼저 적게** 한다 — "장애를 줄인 방식을 우리 일에 붙인다면?" 은
> 붙일 대상이 문장에 없어서 답을 시작할 수 없었다(실측 화면). 세 질문 모두 같은 사다리를 탄다
> (③은 `articles.hypothesis_question` · 마이그레이션 0016). ③의 LLM 질문에는 일반 게이트 위에
> **원인 되묻기 금지**가 한 겹 더 붙는다.
| **인사이트 읽기** | 글 상세 > 인사이트 시트 | 이 글에 달린 인사이트 목록. **인사이트만 떼어 보는 상세 화면은 없다** — 마이·그날 활동에서 인사이트를 누르면 그 글의 시트가 열리고 **그 인사이트 자리로 스크롤**된다(테두리로 짚어 준다) |
| **댓글** | 글 상세 > 인사이트 시트 | 인사이트에 대댓글(스레드·수정·삭제 모두 시트 안에서) |
| **인사이트 공감** | 글 상세 > 인사이트 시트 | 인사이트에 **인사이트 공감**, 댓글엔 **공감**. "좋아요"라고 부르지 않는다 — 좋아요는 소비의 말이고, 읽고 같은 생각에 닿았다는 뜻은 공감이 담는다. 수는 0이면 숨긴다 |

> 인사이트는 **글 상세 안에서만** 오간다. 남의 인사이트만 모아 보는 피드는 없다(→ §4).
>
> 쓰기를 빈 종이로 주지 않는 게 핵심이다. 질문이 있으면 답하기 쉽고, 밑줄을 그어뒀다면
> **그 문장만 재료로** AI가 초안을 써준다(글 전체 요약이 아니다 — 그래야 "내가 본 것"이 남는다).

### 2.3.1 새 글이 혼자 준비되는 순서

새 글은 사람 손을 타지 않고 **한 시간 안에** 읽을 수 있는 상태가 된다(`supabase/distill_cron.sql`).

| 시각 | 단계 | 하는 일 |
|---|---|---|
| :00 | **수집** | 블로그 RSS → 원문 본문까지 저장 |
| :15 | **요약** | 한눈에(무슨 일/왜/그래서) + 질문형 소제목 + 용어. **LLM 2단계** |
| :30 | **분류** | 대분류 1개 + 대표 태그(목적) + 세부 태그 |
| :45 | **보강** | 난이도 배지 · 생각해볼 질문 |

- 예전엔 **사람이 글을 열 때만** 요약이 만들어졌다. 그래서 아무도 안 연 글은 영원히 요약이 없었다
  (779건 중 9건). 그게 목록에서는 "왜 얘만 요약이 되지?"로 보인다.
- 각 단계는 **한 번에 1건**만 처리하고 **최근 30일 글**만 본다. Groq 무료 티어가 하루 20만 토큰이라,
  전부 매시 돌리면 한도를 넘는다. 일감이 없으면 호출 자체가 일어나지 않아 토큰도 안 쓴다.
- **요약은 LLM 을 두 번 부르고, 둘의 역할이 다르다.**
  - **1단계 = 뼈대만.** 블록 앞 140자만 보고 한눈에 3문답 · 소제목 · 근거 블록을 정한다.
    문단은 **칸마다 한 개**만 쓴다 — 여기서 길게 쓰게 했더니 출력이 잘려 **뒤쪽 칸이 통째로
    사라졌다**(칸 6개를 요구했는데 2개만 남았다).
  - **2단계 = 살.** 1단계가 고른 블록의 **전문**을 읽고 문단을 3개로 다시 쓰고 칸의 결말을 붙인다.
  - 2단계가 실패해도 1단계 뼈대는 그대로 저장한다 — 얕아도 있는 게 없는 것보다 낫다.
- **리드에 나열한 것은 칸으로 다 나와야 한다.** "여섯 가지를 만들었어요"라고 써 놓고 칸이 셋이면
  읽는 사람은 "왜 저것만 다뤘지?" 한다(실제로 받은 지적). 못 다룰 것은 리드에서도 꼽지 않는다.
  1단계만 쓰던 때는 모델이 본문의 44%(그나마 문단 앞 140자)만 봐서 "더 들어가 볼까요"가 얕았다.
  2단계가 실패해도 1단계 답은 그대로 저장한다 — 얕아도 있는 게 없는 것보다 낫다.
- 가이드는 `articles.reading_guide` 에 저장되는 **글의 속성**이다(사용자별 데이터가 아니다).
  한 번 만들면 모두가 같은 저장본을 읽는다 — LLM 비용은 **글당 1회**, 조회수와 무관하다.
- **밀린 예전 글은 크론이 아니라 손으로 채운다**: `npm run guide` / `npm run classify`.
- 고른 글에 **시도 시각을 먼저 찍는다**(`guide_tried_at`·`classify_tried_at`, 스키마 §38).
  안 그러면 게이트를 영영 통과 못 하는 글 하나가 매시 다시 뽑혀 하루 치 토큰을 통째로 태운다.

| 2 | **AI 활용** | AI 자체가 주제 — AI로 일하는 방식을 바꿨거나 AI 기능을 만들었다 |
| 3 | **제품·서비스 기획** | 없던 서비스·기능을 내놓았거나 정책·로드맵·운영을 바꿨다 |
| 4 | **데이터·실험** | 지표·분석·가설 검증·A/B 테스트로 판단했다 |
| 5 | **사용자 이해·경험** | 사용자의 문제·행동을 알아냈거나 있던 화면·흐름을 고쳤다 |
| 6 | **사업·브랜드** | 매출·수익화·시장·브랜드 인지 자체가 결론 |
| 7 | **협업·프로세스** | 팀이 일하는 방식이 결론 |

**위에서부터 처음 "예"가 나오는 칸**이 대분류다. "예"라고 답하려면 **본문에서 근거 문장을
그대로 인용**할 수 있어야 한다 — 못 하면 "예"가 아니다.

판정은 같은 글에 **3번** 물어 **두 번 이상 같은 답**이 나와야 채택한다. 흔들리는 글은
분류하지 않고 비워 둔다. 억지로 넣으면 필터 전체를 못 믿게 된다.

#### 그 밖의 찾기

| 기능 | 어디에 |
|---|---|
| **필터** (기업·주제·난이도·정렬) | 피드 |
| **안 읽은 글만** | 피드 |
| **검색** (제목·요약·태그) | 상단 🔍 |
| **기업별 목록** | 출처를 눌렀을 때 |
| **오늘의 추천**(하루 한 편) · 지금 뜨는 아티클 · 주제·기업·서비스 종류별 진입 | 홈 |

#### 홈은 "들어온 사람의 상태" 순서로 세운다

| 칸 | 누구를 위한 칸인가 | 무엇으로 만드나 |
|---|---|---|
| ① 검색 | 찾으러 온 사람 | 제목·요약·태그 |
| ② 지금 뜨는 아티클 | 남들이 뭘 보나 | 인기 1~10위가 **한 줄에 한 개씩** 3초마다 돌아간다. 한 줄이라 맨 위에서 자리를 거의 안 먹는다 |
| ③ 오늘은 이 글 어떠세요? | 맡기는 사람 | 날짜를 씨앗으로 고른 한 편(큰 카드). 새로고침해도 안 바뀐다 |
| ④ 읽다 만 글이 있어요 | 읽다 만 사람 | **밑줄·담은 단어는 있는데 완독 기록이 없는 글**. 없으면 **칸째 사라진다** — 없는 날이 더 많아서 위에 두면 첫인상이 매일 달라진다 |
| ⑤ 기업별로 모아봤어요 | 출처로 찾는 사람 | 로고 **한 줄** 가로 스크롤. **관심 기업이 앞**(작은 별) |
| ⑥ 어떤 이야기를 찾으세요? | 주제를 훑는 사람 | **대분류마다 섹션 하나** — 이름 + 큐레이션 한 줄 + 그 주제 글 캐러셀 |
| ⑦ 서비스 종류별로 모았어요 | 우리랑 비슷한 곳은? | **서비스 종류** 칩(커머스·금융·포털·지역·클라우드) |

- **칸을 열 개에서 여덟 개로 줄였다.** "이런 걸 풀었어요"(목적 태그) · "숫자로 답한 글" ·
  "이번 주 같이 읽고 있어요" · 보라 배너를 뺐다 — 내용이 너무 많다는 말을 들었고, 그 역할은
  대부분 **피드의 필터와 검색**이 이미 한다.
- **"관심 기업의 새 글"은 칸을 따로 두지 않는다.** 기업별 모아보기에서 관심 기업을 앞으로
  정렬해 흡수했다 — 같은 일을 하는 문을 두 개 두지 않는다.
- **이어 읽기는 진행률을 쓰지 않는다.** 저장하는 건 완독 여부뿐이라, "읽던 글"은
  밑줄·담은 단어라는 **손댄 흔적**으로 안다. 담아둔 글(북마크)은 "읽을 글"이라 여기 넣지 않는다.
- **취향 분석은 홈에 두지 않는다 — 마이의 것이다.** 홈은 "새로 읽을 것"을 주는 자리고,
  내 기록을 돌아보는 자리는 마이다. 홈에 얹어 봤지만 아래 대분류 피드와 같은 글이 두 번
  깔리기도 했다.
- **오늘의 추천에 배경을 주지 않는다.** 틴트 박스 + 배지를 얹어 봤지만 되돌렸다 — 큰 카드
  자체가 이미 크기로 구분된다. 배경까지 주면 강조가 두 겹이 되고 칸만 무거워진다.
- **"인기 글" 칸은 뺐다.** 많이 본 글이 내 문제와 상관있다는 보장이 없다. 인기순은
  **피드의 정렬**과 ④ 티커로 남아 있다.
- **목적 태그는 `purpose_tag` 뿐이다.** 본문에 나온 단어를 태그로 쓰면(#AWS #모니터링)
  결국 개발자 언어로 돌아간다(기준 v1 4단계).
- **서비스 종류는 DB 컬럼이 아니라 `src/lib/serviceKind.ts` 의 표가 정본이다.**
  `blogs.kind`(tech/design/product/culture)는 "기술 블로그냐"를 말할 뿐, 무슨 서비스를
  만드는지는 말하지 않는다. **블로그를 새로 추가하면 그 표에도 한 줄 넣는다.**

### 2.5 내 기록

| 기능 | 어디에 |
|---|---|
| **연속 읽기** | 마이 맨 위 큰 카드. 끊기면 0 대신 "오늘 한 편 읽으면 시작돼요" |
| **달력** | 마이 — **이번 주 한 줄**. 활동한 날이 채워지고, 날짜를 누르면 그날 활동 |
| **프로필 편집** | 마이 ⚙ → 설정 → 프로필 편집 |
| **관심 기업** | 마이 ⚙ → 설정 → 읽기 → 관심 기업(별 켜고 끄기, 지금 N곳). 홈의 기업 줄에서도 연다 — 켜 둔 기업은 그 줄 맨 앞으로 온다 |
| **이번 달 수치 · 연속 읽기** | 마이 — 0은 보여주지 않는다 |
| **내 활동 필터** | 마이 > 내 활동 > 필터 — **기간**(최근 7일·30일·올해) / **주제**(대분류) / **기업** / **서비스 종류**. 고를 수 있는 값은 내 활동에 실제로 있는 것만 낸다. 필터로 0건이면 "조건에 맞는 글이 없어요"로 원래 없는 것과 구분해 말한다 |
| **내 활동** | 마이 — **내가 손댄 글 하나 = 카드 하나.** 한 글의 인사이트·밑줄·댓글·용어가 한 카드에 모인다. 머리에 글 제목 · 기업 · 주제 · 마지막으로 손댄 때, 그 아래 "인사이트 1 · 밑줄 3 · 용어 5". 최근에 손댄 글이 위, 카드를 누르면 그 글 (담아둔 글은 아카이브 탭) |
| **인사이트 표시** | 어디서 보든 **질문과 답을 짝으로** 보여준다(`InsightBody`). 답만 떼어 놓으면 무엇에 답한 말인지 모른다 — 마이 카드도 같은 규칙이다 |
| **내 활동 필터** | **한 줄** — 왼쪽에 **필터** 버튼(시트: 기간·주제·기업·서비스 종류, 축마다 하나씩, 고른 수를 "필터 2"로 표시), 오른쪽에 **종류 칩**이 스크롤한다(인사이트·밑줄·댓글·단어, 칩마다 **글 수**). **0건인 칩도 누를 수 있다** — 누르면 "아직 없어요"라고 목록이 말한다. 처음 들어왔을 때만 내용이 있는 칩으로 잡아 준다. "전체"는 두지 않는다. 필터는 **카드가 무엇을 펼칠지**도 정한다 |
| **단어장** | 마이 > 내 활동 > **단어** 필터 — 카드는 글, 안에 그 글의 "알아두면 편해요" 용어(단어 · 영역 · 뜻). 읽기만 해도 쌓인다. 직접 담은 단어는 그 글 줄에 붙어 삭제·"AI 뜻 다시 만들기"가 유지되고, 글을 못 찾는 단어는 "직접 담은 단어" 묶음 |

> 단어장 출처를 바꾼 이유: 예전엔 **문장을 길게 눌러 직접 담은 단어**만 쌓였다. 지금은 글 상세가
> 용어를 미리 뽑아 밑줄까지 그어 주므로 담는 행동이 거의 일어나지 않는다(실제 5개).
> 묶는 기준은 **글**이다. 날짜로 묶으면 "그날 뭘 읽었나"가 되어 달력·활동과 겹치고, 단어만 쭉
> 늘어놓으면 "이 말을 어디서 봤더라"가 사라진다 — 용어는 그 글의 맥락 안에서만 뜻이 산다.
> 영역은 묶는 기준이 아니라 줄에 붙는 꼬리표로 남는다("자주 막히는 영역"이 그 역할을 한다).

> 내 활동을 5개 목록에서 **하나로 합친 이유**: 인사이트·하이라이트·댓글·읽음·단어장은 테이블을
> 나눈 방식 그대로였다. 한 글에 밑줄 3개 + 인사이트 1개 + 용어 5개를 남기면 세 목록을 돌아다녀야
> 전체가 보였고, 목록마다 날짜 헤더 규칙도 달랐다. 사람이 찾는 단위는 **글**이다.
| **내 취향** | 마이 **맨 위 카드**(프로필과 합쳤다) — "OOO님의 취향을 분석해봤어요" + **분포 막대 두 축**: 주제(대분류)와 기업. 막대 길이는 비율, 숫자는 편수, 축마다 최대 4개. **막대만 둔다**(태그 칩은 뺐다). 5편 미만일 때만 문장으로 "몇 편 더 읽으면"이라고 말한다 |
| **자주 막히는 영역** | 마이 — 단어를 누른 기록이 쌓여 학습 지도가 된다 |
| **레퍼런스로 내보내기** | 마이 > 달력 > 그날 활동 — 복사 / 공유 |

#### 레퍼런스 내보내기 템플릿

노션에 그대로 붙이는 마크다운이다. **글 하나 = 블록 하나**로 묶는다.

```
# 2026년 9월 22일 읽은 레퍼런스

## 1. {제목} — {기업}
**한 줄 요약**      가이드의 summary(없으면 글 요약)
**1분 이해**        한눈에 네 질문과 답
**기획 포인트**     있을 때만
**내가 남긴 인사이트** 핵심 / 바로 적용할 것 / 내 해석 / 인상적인 문장 / 비슷한 사례 / 질문
**알아두면 좋은 용어** 용어 — 쉬운 뜻
**하이라이트**      그날 그은 밑줄(인용 + 메모)
**링크** — [원문 보기](url)

## 담은 단어 / ## 남긴 댓글 / ## 읽기만 한 글
```

- **활동 종류별로 나누지 않는다.** 예전엔 인사이트·밑줄·단어·읽은 글을 각각 섹션으로 뿌렸는데,
  붙여넣고 나면 **같은 글의 조각이 네 군데로 흩어져** 무슨 글 얘긴지 알 수 없었다.
  자료로 쓰이는 단위는 활동이 아니라 **글**이다.
- **읽기만 한 글은 맨 뒤 링크 목록.** 자료가 아니라 기록이라, 본문에 섞으면 읽을 블록이 묻힌다.
- 빈 칸은 통째로 뺀다. 활동이 없는 날은 버튼을 그리지 않는다.

## 3. 용어 — 헷갈리면 여기로

| 말 | 뜻 | 헷갈리는 것 |
|---|---|---|
| **인사이트** | 사용자가 글을 읽고 쓴 감상문 | "댓글"이 아니다. 댓글은 인사이트에 달리는 답글 |
| **담기** | 글을 아카이브에 넣는 것 = 저장 | 북마크는 없앴다. 담기 하나뿐이다 |
| **아카이브** | 이름 붙여 묶는 보관함 | 담는 곳이자 저장되는 곳 |
| **한눈에** | 무슨 일 / 왜 했나 / 그래서 뭐가 달라졌나, 세 질문의 답 | 원문 발췌가 아니라 **AI가 쉽게 다시 쓴 것**이다 |
| **더 들어가 볼까요?** | 한눈에를 파고드는 **질문형 소제목** + 답 문단 | 새 개념을 꺼내는 자리가 아니다 — 이미 나온 이야기만 깊이 판다 |

> **왜 시간순 나열을 버렸나.** 한동안 핵심 정리를 "일어난 일을 시간순 한 줄씩"으로 만들었다.
> 실제로 나온 줄은 "원천 데이터에 메타데이터를 붙여 임베딩을 만든다" 같은 것이었다 —
> **개발자가 한 일의 순서**일 뿐, 비개발자가 알아야 할 내용이 아니다. 게다가 "조금 더 자세히"가
> 리드에 없던 개념(컨텍스트 엔지니어링 등)을 소제목으로 들고 나와 거기서 길을 잃게 만들었다.
> 사람이 실제로 묻는 건 늘 셋이다: **무슨 일이야, 왜 했대, 그래서 뭐가 달라졌어.**
> 그래서 질문을 화면에 글자로 적고, 더 파는 칸도 **질문으로만** 연다.
> 서버 게이트가 물음표로 끝나지 않는 소제목을 탈락시킨다.
| **난이도** | easy / terms / code | 사람 등급이 아니라 **글의 성격** |
| **대분류** | 주제 7개(§2.4) | 결론이 무엇인가로 나눈다. 등장 단어로 나누지 않는다 |
| **가이드** | 요약 + 용어 + 한눈에 + 더 들어가를 묶은 것 | AI가 만들고 게이트를 통과해야 저장된다 |

## 4. 안 하는 것 (중요)

**아래는 한때 있었거나 자연스러워 보이지만, 일부러 안 하기로 한 것들이다.**
다시 넣자는 얘기가 나오면 먼저 여기 적힌 이유를 반박해야 한다.

| 안 하는 것 | 왜 |
|---|---|
| **알림** | 읽으라고 조르는 앱이 되면 제일 먼저 지워진다. 돌아올 이유는 아카이브가 만든다 |
| **커뮤니티 자유글** | 글 읽기와 관계없는 글이 섞이면 "읽는 앱"이 아니게 된다 |
| **남의 인사이트 피드** | 인사이트는 그 글을 읽은 사람에게만 의미가 있다. 목록으로 떼면 남의 감상문 모음일 뿐이다 |
| **팔로우 · 인사이터 프로필** | 사람을 따라다니게 만들면 글이 아니라 사람이 중심이 된다 |
| **글 직접 등록** | 수집을 믿게 만드는 게 먼저다. 등록은 그 신뢰를 대신하지 못한다 |
| **스터디 기능** | 이 앱의 전신이었지만 지금 서비스와 목표가 다르다 |
| **읽기시간 표시** | §2.1 참고 |
| **원문을 앱 안에 통째로 싣기** | 한때 원문 문단을 단계로 접었다 폈다. 자르기만 해서는 안 쉬워진다 — 어려운 건 문단 길이가 아니라 문장 자체였다. 원문은 웹뷰로 보러 간다 |
| **키워드 규칙 분류** | 등장 단어로 나누면 같은 단어가 나오는 전혀 다른 글이 한 칸에 몰린다. 대분류는 결론으로 정한다 |
| **결정 카드** (문제·제약·버린 대안·결과) | 실측 70건 중 33건이 빈 껍데기였다. 데이터가 비면 무너지는 구조는 쓰지 않는다 |
| **읽기 습관 강요** (연속 끊김 경고 등) | 숫자로 벌주지 않는다 |
| **북마크** (담기와 별개의 저장) | 버튼 두 개가 나란히 있으면 차이를 매번 생각해야 한다. 실제로는 저장만 하고 분류는 안 해서 두 숫자가 계속 어긋났다 |

> DB 테이블은 **지우지 않았다.** `community_posts` · `app_notifications` · `user_follows` ·
> 스터디 테이블은 그대로 있고 앱에서만 안 쓴다. 되돌리기 쉽게 하려고 일부러 그렇게 뒀다.

## 5. 기능을 바꿀 때

1. **이 문서를 먼저 고친다.** §2에 추가하거나 §4로 옮긴다.
2. 화면이 바뀌면 `DESIGN_GUIDE.md` §7 와이어프레임을, 규격이 바뀌면 `DESIGN_SYSTEM.md` 를 고친다.
3. DB가 바뀌면 `supabase/distill_schema.sql` 에 **새 섹션 번호로 덧붙인다**(기존 섹션 수정 금지 — 재실행 안전해야 한다).
4. 게이트를 돌린다.
   ```
   npx tsc --noEmit
   npx jest
   npx expo export --platform web
   ```
5. 작업 내용을 `HANDOFF_v*.md` 에 남긴다.

### 새 기능을 넣을지 판단하는 질문 세 개

- **읽다가 막히는 걸 없애나?** 아니면 넣지 않는다.
- **AI가 실패해도 화면이 멀쩡한가?** 아니면 구조를 바꾼다.
- **데이터가 비는 글에서도 의미가 있나?** 아니면 결정 카드처럼 껍데기가 된다.
